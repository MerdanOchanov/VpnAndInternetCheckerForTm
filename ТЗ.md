# Техническое задание: InternetChecker

Программа для Windows, живущая в системном трее (или как компактный виджет), которая
двумя индикаторами показывает состояние двух независимых каналов связи.

---

## 1. Назначение

Пользователь работает с включённым VPN. Ему нужно в любой момент видеть/проверить:

1. **Есть ли интернет вообще** — то есть работает ли физический канал до местного
   (туркменского) провайдера **в обход VPN**. Это отвечает на вопрос «у меня упал
   провайдер или упал VPN?».
2. **Работает ли интернет через VPN** — то есть проходит ли трафик через VPN-туннель
   до внешнего мира.

Разделение важно: если VPN «висит» и заворачивает весь трафик в мёртвый туннель,
обычная проверка `ping 8.8.8.8` ничего не скажет о том, жив ли сам провайдер. Поэтому
первая проверка обязана идти мимо VPN, по физическому адаптеру.

---

## 2. Основные требования (кратко)

| # | Требование |
|---|------------|
| 1 | Приложение сворачивается в системный трей (значок в области уведомлений). |
| 2 | Опционально — компактное всплывающее окно-виджет с двумя строками статуса и двумя кнопками. |
| 3 | Кнопка/индикатор №1: «Провайдер (мимо VPN)» — проверка физического канала в обход VPN. |

| 6 | Значок в трее меняет цвет/вид в зависимости от совокупного состояния. |
| 7 | Настройки (адреса для пинга, интервал, автозапуск) редактируются пользователем. |

## 3. Функциональные требования

### 3.1. Проверка №1 — «Провайдер в обход VPN»

**Цель:** убедиться, что физическое соединение с провайдером живо, независимо от того,
поднят VPN или нет.

**Логика:**
- Цель проверки — узел внутри сети туркменского провайдера (например, шлюз провайдера,
  DNS провайдера, или сайт `*.tm`). Конкретный IP/host задаётся в настройках
  (см. §6, значение по умолчанию — **заполнить реальным IP провайдера**, например
  DNS Туркментелеком).
- Проверка **обязана** уходить через **физический сетевой адаптер**, а не через
  VPN-туннель, даже когда VPN активен и является шлюзом по умолчанию.

**Способы обойти VPN (реализовать один, приоритет сверху вниз):**

1. **Bind сокета к IP физического адаптера.** Определить локальный IPv4-адрес
   физического интерфейса (Ethernet/Wi-Fi, не TUN/TAP) и отправлять ICMP/TCP-запрос
   с привязкой источника к этому адресу. В .NET — `Ping` не даёт задать source-адрес
   напрямую, поэтому использовать raw-сокет ICMP (`SocketType.Raw, ProtocolType.Icmp`)
   с `socket.Bind(physicalLocalEndPoint)`, либо TCP-connect к `host:port` с
   привязанным источником.
2. **Временный статический маршрут.** Добавить маршрут до целевого IP через шлюз
   физического адаптера (`route add <target> mask 255.255.255.255 <phys_gateway>
   metric 1`), выполнить проверку, затем маршрут удалить. Требует прав администратора.
3. **Bind по индексу интерфейса** через `SetBestInterface`/`IP_UNICAST_IF` на сокете.

**Определение физического адаптера:**
- Перебрать `NetworkInterface.GetAllNetworkInterfaces()`.
- Исключить адаптеры VPN: по типу (`Tunnel`), по описанию/имени
  (`TAP-Windows`, `WireGuard`, `Wintun`, `OpenVPN`, `WAN Miniport`,
  `*VPN*`), по отсутствию физического MAC.
- Выбрать активный (`OperationalStatus.Up`) адаптер типа `Ethernet`/`Wireless80211`
  с валидным шлюзом.
- Список признаков VPN-адаптеров вынести в настройки, чтобы дополнять.

**Результат проверки №1:**
- `OK` — физический канал жив (ответ получен в пределах таймаута).
- `FAIL` — нет ответа (провайдер недоступен / кабель / Wi-Fi отвал).
- `UNKNOWN` — не удалось определить физический адаптер.

### 3.2. Проверка №2 — «Интернет через VPN»

**Цель:** убедиться, что через VPN-туннель есть реальный выход в интернет.

**Логика:**
- Цель — надёжный внешний узел за пределами Туркменистана (например `1.1.1.1`,
  `8.8.8.8`, либо HTTPS-запрос к `https://www.google.com` / `https://cloudflare.com`).
  Адрес задаётся в настройках.
- Проверка должна идти **через VPN-адаптер**. Если VPN является шлюзом по умолчанию,
  достаточно обычного запроса. Для надёжности — привязать сокет к IP VPN-адаптера
  (найденного по признакам из §3.1).
- Рекомендуется двухступенчатая проверка: сначала ICMP до IP, затем HTTPS-запрос
  (проверяет и DNS, и реальный проход трафика, а не только ICMP).

**Результат проверки №2:**
- `OK` — через VPN есть интернет.
- `FAIL` — VPN поднят, но трафик не проходит (мёртвый туннель / VPN упал).
- `OFF` — VPN-адаптер не найден/не активен (VPN выключен).

### 3.3. Совокупный статус (значок в трее)

| Провайдер | VPN | Значок | Трактовка |
|-----------|-----|--------|-----------|
| OK | OK | 🟢 зелёный | Всё работает |
| OK | FAIL/OFF | 🟡 жёлтый | Провайдер жив, VPN не работает |
| FAIL | — | 🔴 красный | Нет физического интернета |
| UNKNOWN | — | ⚪ серый | Не удалось проверить |

Всплывающая подсказка (tooltip) значка показывает текст обоих статусов и время
последней проверки.

## 4. Пользовательский интерфейс

### 4.1. Трей
- Значок в области уведомлений, цвет по §3.3.
- Клик левой кнопкой — открыть окно-виджет.
- Клик правой кнопкой — контекстное меню: «Проверить сейчас», «Настройки»,
  «Автозапуск (вкл/выкл)», «Выход».

### 4.2. Окно-виджет (компактное, без рамки, поверх остальных — опционально)
```
┌─────────────────────────────────┐
│  InternetChecker                │
│                                 │
│  ● Провайдер (мимо VPN)  ✔ OK   │  [Проверить]
│  ● Интернет через VPN    ✘ нет  │  [Проверить]
│                                 │
│  Обновлено: 14:32:05            │  ⚙
└─────────────────────────────────┘
```
- Две строки: цветной кружок + название + текстовый статус.
- Две кнопки «Проверить» — запускают соответствующую проверку немедленно.
- Кнопка настроек (⚙).
- Окно закрывается по потере фокуса или по клику на значок.

## 5. Нефункциональные требования

- **ОС:** Windows 10 / 11 (x64).
- **Стек (рекомендация):** C# / .NET (WinForms или WPF) — `NotifyIcon` для трея,
  прямой доступ к сокетам и сетевым интерфейсам через `System.Net.NetworkInformation`
  и `System.Net.Sockets`. Альтернатива — Python + `pystray` (но контроль над
  привязкой сокетов беднее).
- **Права:** обычный пользователь для варианта с bind сокета; администратор — только
  если выбран способ со статическими маршрутами. Приложение должно корректно работать
  без прав администратора, деградируя к bind-методу.
- **Ресурсы:** потребление CPU/памяти минимальное; проверки асинхронные, не блокируют UI.
- **Таймауты:** таймаут одной проверки ≤ 3 сек (настраивается).
- **Автозапуск:** опция запуска вместе с Windows (ключ реестра
  `HKCU\...\Run` или ярлык в Startup).
- **Логирование:** локальный лог последних N проверок с временными метками (для
  диагностики), без отправки куда-либо наружу.
- **Приватность:** программа не передаёт данные на сторонние сервисы; все проверки —
  прямые сетевые запросы к адресам из настроек.

## 6. Настройки (конфигурация)

Хранить в JSON-файле рядом с программой (или в `%APPDATA%`).

| Параметр | Значение по умолчанию | Описание |
|----------|----------------------|----------|
| `providerTarget` | *(заполнить: IP/host туркм. провайдера)* | Цель проверки №1 |
| `providerCheckType` | `icmp` | `icmp` или `tcp:<порт>` |
| `vpnTarget` | `1.1.1.1` | Цель проверки №2 (IP) |
| `vpnHttpTarget` | `https://cloudflare.com` | HTTPS-цель проверки №2 |
| `checkIntervalSec` | `15` | Интервал авто-проверки |
| `timeoutMs` | `3000` | Таймаут одной проверки |
| `vpnAdapterHints` | `["TAP","WireGuard","Wintun","OpenVPN","VPN"]` | Признаки VPN-адаптеров |
| `autostart` | `false` | Запуск с Windows |
| `bypassMethod` | `bindSocket` | `bindSocket` \| `staticRoute` |

## 7. Порядок сдачи / критерии приёмки

1. При выключенном VPN обе проверки корректно определяют состояние (провайдер OK,
   VPN = OFF).
2. При включённом рабочем VPN — обе проверки OK.
3. При включённом VPN с «мёртвым» туннелём (например, отключить интернет у VPN-сервера,
   имитировав) — проверка №1 = OK, проверка №2 = FAIL. **Это ключевой сценарий.**
4. При выдернутом кабеле / отключённом Wi-Fi — проверка №1 = FAIL, значок красный.
5. Значок в трее и tooltip отражают состояние по таблице §3.3.
6. Кнопки «Проверить» дают результат за ≤ таймаут.
7. Приложение работает без прав администратора (метод `bindSocket`).

   статических маршрутов)?
